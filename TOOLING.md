# Tooling reference

This repository keeps runtime UI assets build-free. Python packages below are
**development / verification tools only** and are not web-ui runtime dependencies.

## Browser automation

Stagehand v4 is available as a Python SDK (`stagehand`) as well as
TypeScript and Go SDKs. web-ui treats it as an optional browser-agent lane next
to deterministic Playwright smoke tests, not as a replacement for Playwright.

Reference baseline when this integration was introduced:

- Stagehand major: **v4**
- observed PyPI release: **4.1.0**
- checked: **2026-09-23**
- Python: **3.11+ for the current PyPI v4 package**
- local browser execution requires Chrome/Chromium; remote Browserbase use
  requires credentials

The required Stagehand v4 surface contract is deliberately small:

- the Python package imports successfully
- it exposes `Stagehand` or `AsyncStagehand`

Browser launch, navigation, extraction, `act`/`observe`, and live agent behavior
are **not** required CI contracts yet. Those operations cross into browser/model
integration and should remain opt-in tests.

Live Stagehand tests must be opt-in. Local browser tests may use local
Chrome/Chromium. Remote Browserbase tests must receive credentials through
GitHub Actions secrets/environment at execution time; credentials must never be
committed, emitted by `repository_metadata.py tooling`, or uploaded as artifacts.

## Tool diagnostics

Install development dependencies with uv and run them from that environment.
pytest is a dev dependency with a lower bound only (`pytest>=8`).

Stagehand is not installed by default. It is the opt-in `stagehand` dependency
group (`stagehand>=4`), so `uv sync` and `uv run pytest` do not pull browser
tooling. Tests that need it use `pytest.importorskip` and skip without the group;
the CI lane (`ci.yml`, job `tooling`) runs them with `--group stagehand`, so the coverage is unchanged.

`pyproject.toml` sets `[tool.uv] override-dependencies` to lift transitive
ceilings until upstream metadata catches up: Gradio 6.30.0 caps `pillow<13`,
`safehttpx<0.2`, and `tomlkit<0.15` (Pillow 13+ addresses Dependabot JPEG CVEs);
Playwright caps `pyee<15`. The pyee override is a lower bound (`pyee>=13`) so
Python 3.12 and newer can take pyee 15, while Python 3.11 stays on a pyee
release that supports it. Drop each override when the parent package allows the
current PyPI release without conflict.

```sh
uv run pytest -v
uv run --group stagehand pytest -v
uv run --locked --group stagehand python tools/repository_metadata.py tooling
python -S tools/repository_metadata.py repo-metadata --format v1 --repository myon-bioinformatics/PySaiyanWeBoo --root . --output-dir /tmp/PySaiyanWeBoo-metadata
```

`repository_metadata.py tooling` probes Python runtime and Git/GitHub CLI/Node/npx versions
locally (stdlib only; the former vendored `gh_identity.tool_versions()` copy was
removed), and observes the explicitly allowlisted `pytest`/`stagehand` distributions
(`stagehand` is reported only when its group is installed). The consumer only
timestamps and projects those observations into the existing `runtime`, `commands`,
and `packages` JSON groups.
It does not collect repository identity or add app/render/build measurements.

Available values are canonical normalized short version strings (for example,
Git `2.45.1`, rather than `git version 2.45.1`). Missing, failed, malformed or
unmeasured observations are **omitted**, never replaced with `null` or `unknown`.
Empty groups remain `{}`; consumers must handle absent keys. Duplicate canonical
owners are errors even when a tool is unavailable. No consumer values are merged
over canonical keys. Command probes use the producer's 5 second timeout;
`WEB_UI_TOOL_TIMEOUT` is no longer used.

Repository identity is generated by local `tools/repository_metadata.py`
(`repo-metadata --format v1`; same Ironmate v1 JSON/JSONL contract). Remaining
vendored source identity and byte hashes live only in `vendor.lock.json`; refresh
entries with the pinned parent `vendor_sync.py` workflow, not per-file sidecars.
`gh_identity` is no longer vendored here — use the independent
`myon-bioinformatics/gh_identity` repository when that surface is needed.

CI's existing `tooling-meta` artifact contains three separate files:
`tooling-meta.json` (advisory observations), `repository-metadata.json`, and
`repository-metadata.jsonl` (the same canonical record). Measurements remain
`null` unless measured. The `repository-diagnostics.js` module (Python data in `pysaiyanweboo.py`) only reads/renders the
canonical record; it never recollects Git identity. This is the first consumer
slice of Ironmate #49; Flutter and other consumers remain separate follow-ups.
The CLI retains the repository-metadata v1 output fields and JSON/JSONL identity
path. Its `tooling` field is always `{}`; version observations are emitted only
in `tooling-meta.json`. The local Python validator accepts a tooling dictionary
without the former GHI key/value label restrictions. This is a narrower local
producer, not a promise of full compatibility with GHI's optional Python API.

### What can fail CI

- required API/surface contract break: **fail**
- required Git/GitHub tooling missing: **fail**
- invalid/missing repository SHA metadata: **fail**
- newer tool/package version exists: **pass**
- optional live Stagehand integration is not configured: **pass**

## Policy

- deterministic browser smoke: Playwright/Chromium
- agent-oriented browser experiments: Stagehand v4
- GitHub automation/diagnostics: `git` + `gh`
- pytest tests run with `uv run pytest`; stdlib unittest lanes stay on `python -m unittest`
- application/runtime UI remains build-free and dependency-light
- version/SHA metadata should aid diagnosis, not cause needless failures merely
  because a newer tool release exists


## Reuse in other repositories

This repository defines the web-ui verification pattern only. Other repositories may copy or adapt the deterministic smoke, advisory metadata, pytest, or Stagehand pieces independently. References to `flutter_navigation_basic`, Ironmate, `mcp-toolcall-lab`, or future projects are examples, not requirements or cross-repository contracts.

### Accepting future Flutter functionality

Keep the default environment small when receiving functionality from Flutter. Put new framework/browser/service dependencies in a named opt-in dependency group for the feature. Reuse `gradio` for Gradio/Playwright integration and `stagehand` for browser assistance; enable both explicitly only when a feature needs both. Do not add these packages to `dev` merely to avoid local skips.

Every optional feature must have an enabled CI lane that installs its group and actually executes its required tests. A local `importorskip` is acceptable only when a corresponding enabled lane proves the test passes. Compare default and enabled environments, inspect skip reasons, preserve browser evidence, and record package/size measurements with conditions before expanding dependencies.

## Focused standard-library test discovery

Run from this repository root with Python 3.11 or newer. These commands use
Python’s built-in test runner; the listed checks need no third-party Python
package or browser installation. `-S` disables automatic `site` initialization
and its usual site-packages path additions; it is not a complete isolation boundary.

```sh
python -S -m unittest discover -s tests -p test_pages.py -v -k EmbeddedModulesTests
```

Validated on Linux / CPython 3.12.14: **6 tests, exit 0** (2026-11-03).

To narrow the first command to a test name, use the built-in `-k` filter:

```sh
python -S -m unittest discover -s tests -p test_pages.py -v -k test_the_embedded_module_is_the_one_source_of_ui_js
```

`-s` is the discovery start directory, `-p` matches test filenames, `-k`
filters test names, `-v` prints each executed test, and `-f` stops at the first
failure. Quote filename patterns so the shell does not expand them. Check the
final `Ran N tests` line: zero tests is not a successful verification, even
though unittest can exit 0. `-k` runs selected tests; it is not a list-only mode.

These are focused checks, not the complete project suite. Keep the existing
pytest/CI command for full coverage and native JUnit or fixture support.
Unittest does not collect module-level pytest functions or apply pytest
fixtures, parametrization, markers, conftest hooks or configured pythonpath.
A broad `test*.py` pattern can import pytest-only modules and fail under `-S`.
Do not add an extra CI pass over tests already owned by pytest just to expose
this local command. No custom discovery runner is required.


## Python JUnit evidence

The primary Python lane uploads its ordinary pytest JUnit XML and the controlled
child's evidence as separate `junit-*` Actions artifacts (14 days, including
producer failure). Raw diagnostics are not published to Pages. The exact two XML
paths are inputs to the pinned shared JUnit identity collector; missing, malformed
or truncated reports fail collection. Ordinary pytest failures still fail the
producer and workflow.

The controlled child is intentionally red inside a green regression. It runs with
and without JUnit, checks both exit codes are 1, and uses the shared xprobe importer
to check failure/setup-error identities and sentinel redaction. Compact context
has `commit_sha=null`; this lane does not infer provenance from Git or connect the
canonical metadata producer.

The importer is test-only and byte-verified before loading. CI checks out upstream
xprobe at `7e7015b2df69ad446b968f6fa49711b5b1dbdd3f` into `.junit-tools`.
Local `uv run pytest` runs skip this optional integration regression when the importer
is absent. CI and explicit evidence runs require it and fail if it is missing.
To exercise the regression locally, place that commit's `xprobe.py` in
`.junit-tools/xprobe.py` first (Git blob `dbc5b7d55005d6288c072a7612584d6170c216f4`).
No runtime import or dependency is added.

The regression exercises the existing missing-command tooling probe with
deterministic monkeypatching. The locked vendor job runs the regression too,
but only the primary tooling job produces reports for this collector. Node,
canonical metadata, screenshots and Pages reporting remain separate. See
[pages-ownership.md](docs/pages-ownership.md) for GitHub Pages evidence publishing policies.


## Visual regression baselines

`tests/visual-baseline/` is the reviewed PNG baseline lane for deterministic Chromium
captures.

Current policy:

- pull requests always generate candidate screenshots;
- if a reviewed baseline exists, exact PNG equality is checked;
- if no baseline exists, CI reports `missing-baseline` but does not fail;
- a future enforcement switch may pass `--require-baseline` once reviewed
  baselines are committed for all stable fixtures;
- baseline changes must be intentional and reviewed together with the UI change.

The first stable target is `contract/v1/example.html`. Gallery/example pages
may also receive baselines, but the frozen contract fixture has priority.


### Candidate selection

The default checker pattern is `web-ui-*.png`, meaning every deterministic
screenshot produced by the current CI lane is visible in the candidate report.

Enforcement may be rolled out more narrowly with `--pattern`, for example:

```sh
python tools/check_visual_regression.py \
  --candidate-dir . \
  --pattern "web-ui-contract-*.png" \
  --require-baseline
```

This lets the frozen contract fixture become blocking before gallery/demo
screenshots do.

The directory is created with the first reviewed baseline; until then every
candidate reports `missing-baseline`.
